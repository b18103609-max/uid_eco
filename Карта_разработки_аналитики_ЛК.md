# Карта разработки и доработок прототипа аналитики ЛК

**Дата анализа:** 01.09.2026  
**Основание:** новая продуктовая спецификация аналитики и трассировка компонентов к источникам данных  
**Объект анализа:** текущий React/Vite-прототип `uid_eco`

## 1. Резюме

Текущий прототип хорошо покрывает операционные реестры и карточки договоров, нарушений и ПКМ. Эту часть нужно сохранить и использовать как целевые точки drill-down.

Аналитическая часть пока не соответствует новой модели. Сейчас это один крупный мок-дашборд `ContractsIndicators`, встроенный во вкладки реестров. Целевая модель — отдельный раздел «Аналитика» из восьми страниц с едиными фильтрами, состояниями данных, расшифровкой сегментов и переходами в существующие объекты.

Главный риск текущей реализации — не недостаток графиков, а наличие показателей, которые не разрешены новой трассировкой. До наращивания UI нужно убрать ложные бизнес-сигналы и зафиксировать расчетные правила.

## 2. Что есть сейчас

### 2.1. Что можно переиспользовать

| Существующая часть | Роль в целевом решении | Степень переиспользования |
|---|---|---|
| Хаб «Управление исполнением договора» | Родительская точка входа; добавить плитку «Аналитика» | Высокая |
| Реестр и карточка договора | Drill-down из договорной аналитики | Высокая |
| `FlagmanRating` | Операционная таблица/детализация из PAGE-RATING | Средняя; не заменяет аналитическую страницу |
| Реестры и карточки нарушений | Drill-down из четырех вкладок PAGE-SAFETY | Высокая |
| Реестр, создание и карточка ПКМ | Drill-down из PAGE-PCM; операционный сценарий остается без изменений | Высокая |
| Chart.js и текущие визуальные токены | База для `ChartCard` и графиков | Средняя; нужна компонентизация |
| Текущие multi-select и карточки | Визуальный референс для `GlobalFilterBar`, `KpiCard`, `ObjectPreviewCard` | Средняя |

### 2.2. Ключевые расхождения

1. **Нет отдельного раздела «Аналитика».** Аналитика пока встроена как вкладка «Показатели» в договоры, нарушения и ПКМ.
2. **Нет восьми целевых маршрутов.** `App.tsx` переключает экраны локальным `useState`, поэтому URL, deep-link, back/forward и сохранение контекста не работают.
3. **Нет единого каркаса.** Отсутствуют `AnalyticsPageShell`, поднавигация, заголовок с актуальностью, панель внимания, расшифровка сегмента.
4. **Фильтры локальны и неполные.** Сейчас есть период, подрядчик, категория и услуга. Нет ДО, договора, бригады, объекта, сравнения, дополнительных фильтров и переноса состояния между страницами.
5. **Нет общих состояний данных.** Реализованы лишь частные empty-state реестров; нет loading, partial, error, stale и preliminary.
6. **Нет взаимодействия с графиками.** Клик не обновляет `SegmentDetails`, нет `AttentionPanel`, нет перехода в реестр с контекстом.
7. **Нет каталога отчетов.** Есть только неактивный баннер ИДП.
8. **Мок-данные не объединены в предметную модель.** Графики строятся из независимых массивов и коэффициентов; нельзя проследить объект от KPI до карточки.
9. **Монолитная реализация.** `ContractsIndicators.tsx` содержит данные, формулы, прямую работу с DOM, фильтры и все графики в одном файле. Это затруднит постраничные состояния, повторное использование и тесты.

## 3. Критические доработки по корректности данных

Это приоритет **P0**: текущий UI показывает несколько метрик, которые новая трассировка прямо запрещает выдавать за подтвержденные.

| Текущий компонент | Проблема | Решение |
|---|---|---|
| «Итоговый скор» подрядчика | Вычисляется как среднее четырех самодельных субиндексов. Новые требования запрещают сводный индекс без методики | Удалить. Рейтинг бригад показывать только по `final_rating_scores` и `final_rating_colour` |
| «Просрочено», «план vs. факт» и график просроченных ПКМ | В `contract_measure` не подтверждены контрольная и фактическая даты | Заменить на допустимые метрики: количество, статус, категория, сумма, без ответственного, наличие связи с нарушением |
| Мотивация «при наличии критичных нарушений» | Требует стабильной связи и правила атрибуции, которые не зафиксированы | Убрать из базового прототипа. Оставить только прямые суммы мотивации из FORM-IDP |
| Цветовая классификация рейтинга по локальным порогам `85/75` | Цвет должен приходить из `final_rating_colour`, а не вычисляться UI | Заменить локальную функцию `totalClass` на прямой атрибут мок-записи |
| «Данные обновлены» с текущей датой браузера | Не отражает свежесть источника | Ввести `DataFreshness` в мок-данные: статус, время последней загрузки, полнота, предупреждение |
| Порог 70% для доли принятых претензий | В требованиях нет такого порога | Убрать красную линию или зафиксировать порог как отдельно утвержденное правило |

## 4. Целевая карта разработки

```text
Согласование метрик и зерна данных
             │
             ├──→ Каталог метрик и мок-модель со связями объектов
             │                    │
             │                    └──→ Селекторы, агрегации, состояния данных
             │
             └──→ Роутинг + AnalyticsPageShell + GlobalFilterBar
                                      │
                                      ├──→ Итерация 1: Overview + Rating + Safety 1/3
                                      │                 │
                                      │                 └──→ drill-down в реестры/карточки
                                      │
                                      ├──→ Итерация 2: PCM + DPR + Safety 2/4
                                      │
                                      └──→ Итерация 3: Indicators + Addendums + Reports
                                                        │
                                                        └──→ Полный QA состояний и трассировки
```

### 4.1. Слой маршрутов

Добавить реальный URL-роутинг с восемью маршрутами:

| Страница | Route |
|---|---|
| Обзор | `/tdk/analytics` |
| Договоры и индикативные показатели | `/tdk/analytics/indicators` |
| Динамика рейтинга бригад | `/tdk/analytics/rating` |
| Нарушения и оценки ПБ | `/tdk/analytics/safety` |
| ПКМ | `/tdk/analytics/pcm` |
| Допретензионная работа | `/tdk/analytics/preclaim` |
| Дополнительные соглашения | `/tdk/analytics/addendums` |
| Стандартные отчеты | `/tdk/analytics/reports` |

Вкладки «Показатели» в реестрах не должны создавать дублирующую аналитику. Их следует заменить контекстной ссылкой в соответствующую страницу либо полностью убрать.

### 4.2. Общий компонентный каркас

Реализовать до предметных страниц:

- `AnalyticsPageShell` — хлебные крошки, заголовок, свежесть, помощь, скачивание отчета;
- `AnalyticsSubnav` — восемь страниц в целевом порядке;
- `GlobalFilterBar` — не более пяти фильтров первого уровня, дополнительная панель, теги, «Применить» и «Сбросить все»;
- `KpiCard` — значение, единица, сравнение, текстовая интерпретация, tooltip с формулой;
- `ChartCard` — бизнес-вопрос, график, легенда, tooltip, пустое/частичное/ошибочное состояние;
- `DimensionSwitcher` — переключение бригада/ДО/подрядчик и аналогичных разрезов;
- `AttentionPanel` и `AttentionItem` — до пяти объяснимых сигналов;
- `SegmentDetails` и `ObjectPreviewCard` — до пяти объектов выбранного сегмента;
- `DataFreshnessBadge` и `DataState` — `actual`, `delayed`, `partial`, `loading`, `empty`, `error`, для рейтинга также `preliminary`;
- `ReportCard`, `GenerateReportDialog`, `AsyncReportStatus` — каталог и имитация асинхронного формирования.

### 4.3. Слой данных прототипа

Вынести мок-данные из UI-компонентов в связанную предметную модель:

- `subsidiaries`, `contractors`, `services`, `contracts`;
- `brigades`, `ratingResults`, `ratingBreaches`, `stopFactors`, `selfAssessments`;
- `contractBreaches`, `measures` и физическая связь `measureBreachLinks`;
- `preclaimCases`;
- `addendums` с маршром и нормативом;
- `reportDefinitions` и `reportJobs`;
- `dataFreshness` по каждому источнику.

Минимальный объем: 3 ДО, 6 подрядчиков, 15–20 договоров, 12 месяцев, 10–15 бригад, 100–150 рейтингов, 80–120 нарушений, 40–60 ПКМ, 30–50 случаев ДПР и 30–50 ДС.

Каждый KPI и график должен получаться из типизированного селектора, а не из автономного массива в файле страницы. Это обеспечит согласованные фильтры, drill-down и тестируемость формул.

### 4.4. Каталог метрик

Ввести единый `MetricDefinition`:

```ts
type MetricDefinition = {
  id: string;
  label: string;
  status: 'P' | 'R' | 'O';
  source: 'FMD-CONTRACTS' | 'FORM-IDP' | 'FORM-DPR' | 'FORM-DS';
  grain: string;
  unit: string;
  sourceFields: string[];
  formulaId?: string;
  aggregationRule?: string;
  drilldownTarget?: string;
};
```

Компоненты со статусом `O` не рендерятся. Компоненты `R` включаются только после фиксации зерна и агрегации; до этого в макете показывается маркер «Расчетная метрика», но не несогласованная формула.

## 5. Карта страниц

| Страница | Что есть | Что сделать | Повторное использование |
|---|---|---|---|
| **PAGE-OVERVIEW** | Хаб с двумя договорными виджетами и статичным блоком рейтинга | Создать отдельный обзор: 5 KPI, 3 графика, attention, карточки разделов. Хаб не заменять обзором | Общий стиль карточек и Chart.js |
| **PAGE-INDICATORS** | Блоки «Договорные данные», «Финансы», «Мотивация» | Объединить в одну договорную страницу; добавить физический/финансовый план-факт, ОЭДК, риск, scatter; убрать локальный скор | Часть графиков и фильтров после рефакторинга |
| **PAGE-RATING** | Иерархическая таблица с одним периодом | Добавить 6 KPI, динамику балла, зоны, сравнение измерений, переходы зон, блоки оценки, preliminary-state | Таблица как drill-down; пороги UI не переиспользовать |
| **PAGE-SAFETY** | Реестры рейтинговых и договорных нарушений; набор общих графиков | Разделить на 4 вкладки: ВА/ВК/прочие, самооценка, стоп-факторы, другие договорные нарушения | Фильтры, heatmap, реестры и карточки |
| **PAGE-PCM** | Полный операционный flow и частичный дашборд | Пересобрать аналитику без просрочки: 6 KPI, динамика создания, статусы, категории, договоры, связи с нарушениями | Все операционные экраны; не переиспользовать deadline-логику |
| **PAGE-PRECLAIM** | Три мок-графика внутри общего дашборда; плитка хаба не активна | Создать полную страницу: этапы, поступления, aging, финансовый результат, категории, рейтинг подрядчиков/услуг | Часть графиков после перепривязки к FORM-DPR |
| **PAGE-ADDENDUMS** | Нет | Реализовать с нуля: статусы, этапы, маршруты, сроки, динамика, подтипы, изменение договора | Общий каркас и паттерны графиков |
| **PAGE-REPORTS** | Неактивный баннер ИДП | Каталог, поиск, фильтры, диалог регламентных параметров, асинхронные статусы. Для SAFETY/PCM/TEAM — только карточка и пометка о неготовом шаблоне | Баннер как точка входа |

## 6. Поэтапный план

### Этап 0. Корректность и контракт данных — P0

1. Согласовать восемь открытых расчетных правил из раздела 8.
2. Создать `MetricDefinition` и каталог P/R/O.
3. Удалить/скрыть неподтвержденные метрики текущего дашборда.
4. Подготовить связанные мок-данные с заданными демо-сценариями.
5. Добавить юнит-тесты для каждого расчета `R`.

**Результат:** UI не показывает недоказуемые показатели; каждая метрика имеет источник, зерно и формулу.

### Этап 1. Платформа аналитики — P0

1. Ввести URL-роутинг и восемь маршрутов.
2. Добавить плитку «Аналитика» в хаб на одном уровне с реестрами.
3. Реализовать `AnalyticsPageShell` и `AnalyticsSubnav`.
4. Реализовать `GlobalFilterBar` с общим состоянием и синхронизацией с query string.
5. Создать базовые KPI, chart, attention, segment и data-state компоненты.
6. Добавить общие loading, empty, partial и error fixtures.

**Результат:** любая новая страница собирается из готового каркаса и получает общие фильтры.

### Этап 2. Главный демо-сценарий — P1

1. PAGE-OVERVIEW.
2. PAGE-RATING: главные три графика и переданные блоки оценки.
3. PAGE-SAFETY: вкладки «ВА/ВК и прочие» и «Стоп-факторы».
4. Клик по графику → `SegmentDetails` → карточка бригады/нарушения.
5. Переходы Overview → Rating → Safety → существующий реестр.

**Результат:** демонстрируется сквозной сценарий от общего сигнала до предметного объекта.

### Этап 3. Операционные процессы — P1

1. PAGE-PCM без deadline-метрик.
2. PAGE-PRECLAIM по FORM-DPR.
3. PAGE-SAFETY: «Самооценка» и «Другие нарушения по договору».
4. Переходы в ПКМ, нарушение, договор и контрагента.
5. Ссылки на действующие формы отчетов без имитации неполученных шаблонов.

### Этап 4. Договорный контур и отчеты — P2

1. PAGE-INDICATORS после физического маппинга FORM-IDP.
2. PAGE-ADDENDUMS с различными нормативами по маршрутам.
3. PAGE-REPORTS.
4. `GenerateReportDialog` и асинхронные состояния с задержкой 1–2 секунды.
5. Контекстные действия «Скачать стандартный отчет».

### Этап 5. QA и готовность — P1

1. Пять общих состояний на каждой странице.
2. Preliminary-state рейтинга.
3. Три состояния формирования отчета.
4. Клавиатура, focus-state, текстовые альтернативы цвету, доступное объяснение canvas-графика.
5. Адаптивная проверка для ноутбука и узкого desktop; mobile не является первичной целью.
6. Тесты селекторов, фильтров, роутинга, drill-down и отчетного flow.

## 8. Решения, без которых нельзя фиксировать числа

До системного анализа и финальной сборки моков нужно утвердить:

1. зерно каждой витрины;
2. уникальность договора до физического ID-маппинга;
3. агрегацию ОЭДК и `final_rating_scores`;
4. правило выбора предыдущего периода для перехода зоны;
5. словари статусов, рисков, тяжести и цветовых зон;
6. горизонт сигнала по исковой давности;
7. маршрутные нормативы ДС;
8. допустимость аналитики по предварительным рейтингам.

До согласования допустим каркас и подпись «Расчетная метрика», но не демо-число, которое выглядит как согласованная метрика.

## 9. Что не нужно переделывать

- Ролевую модель, RLS и системную архитектуру бэкенда — это вне границ прототипа.
- Экранные Excel-таблицы — стандартные формы должны только скачиваться.
- Универсальный конструктор отчетов, произвольные SQL/формулы, подписки, рассылки и AI-интерпретацию.
- Существующие реестры, карточки и поток создания ПКМ — они нужны аналитике как конечные объекты.

## 10. Критерии готовности доработанного прототипа

Прототип готов к обсуждению, если:

1. есть отдельная точка входа в аналитику и восемь URL-страниц;
2. все страницы используют один каркас и сохраняемые фильтры;
3. главные страницы не перегружены и показывают не более трех основных графиков до прокрутки;
4. клик по графику раскрывает до пяти объектов, а «Показать все» ведет в реестр;
5. все переходы к договору, бригаде, нарушению, ПКМ и ДС работают;
6. рейтинг не пересчитывается и берется из `contracts.gtm`;
7. нет просрочки ПКМ, повторности, сводного индекса и других показателей без подтвержденного поля/правила;
8. каждый KPI и график имеет P/R-статус, источник, зерно и формулу;
9. реализованы все состояния данных и отчетов;
10. точные шаблоны есть только у IDP, DPR и ADDENDUMS; SAFETY и PCM не имитируют неполученную структуру файла.
